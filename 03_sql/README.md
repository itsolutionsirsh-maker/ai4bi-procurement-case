## Q1. OTIF по поставщикам

**Определение OTIF** (подробно в `02_model.md`, 2.5):
- Единица — строка заказа в последней версии, только активные.
- В месяц строка попадает по **плановой дате поставки**.
- Строка = OTIF, если количество со статусом `accepted`, принятое к плановой дате (дата приёмки переведена из UTC в **МСК**), ≥ заказанного.
- Нет приёмки к сроку — не OTIF. Ранняя поставка и перепоставка не штрафуются, `partially_rejected` не засчитывается (в событии нет принятого количества).

**Решения:**
- Период: февраль–июль 2026. Август неполный, его не берём.
- «Поставка» для порога ≥ 20 — это строка заказа с плановой датой в периоде.
- Поставщик = мастер-поставщик (дубли по ИНН склеены).
- Класс надёжности — SCD2-версия на 31.07.2026.
- Динамика: сетка «поставщик × месяц», чтобы `LAG` не перескакивал через пустой месяц. Изменение в п.п. к предыдущему месяцу.
- Ранг — `rank()` внутри класса по OTIF за период, при равенстве ранги одинаковые. Ранг и MoM считаются по неокруглённым долям, округляется только вывод.
- `otif_ci_low_pct` — нижняя граница 95% доверительного интервала (метод Уилсона).

**Результат:** 120 поставщиков × 6 месяцев = 720 строк. Все 120 проходят порог (минимум 43 поставки). OTIF за период: от 32,7% до 60,9%. Лидеры классов: A — S1070 (58,7%), B — S1095 (60,7%), C — S1106 (60,9%). У S1050 189 поставок, потому что к нему приклеен дубль S1128. Без склейки он делился бы на двух «поставщиков».

**Как читать этот рейтинг.** При ~80 поставках на поставщика за полгода погрешность OTIF около ±11 п.п., а месячный OTIF считается в среднем по 14 строкам (бывают месяцы и без поставок). Разброс OTIF между поставщиками на пилотной выгрузке статистически неотличим от случайного (χ² однородности = 135,8 при 119 ст. св., p ≈ 0,14). Средний OTIF классов почти одинаковый: A 44,6%, B 46,2%, C 45,5%. Поэтому запрос отвечает на вопрос задания, но показывать директору «место в рейтинге» я бы не стал: только вместе с интервалом. Нижняя граница 95% интервала выше средних 45,5% у 6 поставщиков, но при 120 сравнениях около 3 таких «выше среднего» получится случайно. С поправкой на множественные сравнения (Бонферрони) таких поставщиков ноль. Вывод для пилота: выделять «надёжных» и «ненадёжных» по OTIF за полгода рано. На полной истории и всех 900 поставщиках картина может быть другой.

## Q2. Ценовые аномалии

**Период:** 2026-Q2 (01.04–30.06.2026), это последний полный квартал при дате 12.08.2026.

**Логика:**
- Средневзвешенная цена поставщика по позиции за базовую ЕИ в рублях: Σ сумм / Σ количества в базовых ЕИ.
- Сравнение с медианой средневзвешенных цен **других** поставщиков, минимум 2 других.
- В выдачу идут строки с |отклонением| > 15%, сортировка по денежному эффекту.

**Главное решение — сравниваю позицию внутри одной ЕИ закупки.** Буквальная версия «всё в базовые ЕИ» на этих данных выдаёт фиктивные −99,9% и «эффект −6 млрд ₽» на закупке в 0,4 млн. Цена в выгрузке не зависит от упаковки, и тонна при делении на 1000 выглядит в тысячу раз дешевле килограмма (AI_LOG, случай 1). Цена в выдаче всё равно показана за базовую ЕИ. Заказы в CNY исключены (дефект D7).

**Результат:** 15 строк. Эффект: от −5,8 до +5,3 млн ₽ на позицию. Знак «+» — переплата, «−» — дешевле медианы. Переплата всегда меньше суммы закупки. «Экономия» может быть больше неё: цена на 95% ниже медианы даёт эффект в 19 раз больше закупки, и это скорее ошибка данных, чем удача. Для отчёта «где переплачиваем» Смирнову фильтр меняется на `money_effect_rub > 0` (строка уже есть в запросе, закомментирована).

**Честное ограничение.** В квартале у поставщика по позиции почти всегда одна строка заказа (`our_lines` = 1), медиана считается по 2–3 другим поставщикам. Главное — цена в выгрузке не зависит от позиции: разброс внутри позиции такой же, как по всему массиву (CV 0,58 и 0,58, дефект D16). Под порог 15% попадает 582 из 666 пар «позиция × поставщик» (87%), у 665 из них — одна строка заказа. Запрос методически корректен и заработает на нормальных данных, но его выдача на этой выгрузке — шум, и заказчику я её не показываю до ответа 1С (вопросы 4–5).

## Q3. Концентрация поставщиков

**Решения:**
- Период: 12 полных месяцев (08.2025–07.2026). В задании он не задан, 12 месяцев сглаживают сезонность.
- Оборот = активные строки в рублях. Поставщик = мастер.
- «Сколько поставщиков дают 80%» считаю **включая** поставщика, на котором накопленная доля переходит через 80%. Условие: доля **до** него < 80%.
- Окно `ROWS`, а не `RANGE` по умолчанию: при равных суммах `RANGE` выдал бы обоим поставщикам одинаковую накопленную долю.

**Результат:** в каждой из 10 категорий (и в «(нет в справочнике)») работают все 120 поставщиков пилота, и для 80% оборота нужно 77–82 из них (в «(нет в справочнике)» — 73). Это **отсутствие концентрации**: ни у одного поставщика нет доли больше 2,6%. На реальных данных так не бывает, и ровно это я бы первым вынес на обсуждение с Ковалёвой. Либо пилотная выгрузка собрана так, что смешала категории, либо закупки действительно размазаны, и тогда это повод для консолидации. «(нет в справочнике)» идёт отдельной строкой, чтобы итог сходился с общим оборотом.

## Где будет проблема с производительностью на объёме ×100 и что делать

×100 — это ~5,5 млн строк заказов и ~6,4 млн приёмок, для PostgreSQL объём всё ещё нормальный. Узкие места:

1. **Q2, self-join «каждый поставщик × каждый другой поставщик» внутри позиции.** Это квадрат по числу поставщиков позиции, а `percentile_cont` сортирует каждую группу. Если поставщиков на позицию станет не 3–5, а 50, join вырастет в сотни раз.
   Что делать: заранее агрегировать витрину «позиция × поставщик × квартал» (зерно `supplier_price`, это тысячи строк, а не миллионы). Медиану «без себя» считать приближённо: медиана по всем поставщикам с поправкой, если поставщиков ≥ 5. Точную leave-one-out оставить только для позиций с 2–4 поставщиками.
2. **Витрина OTIF и `fct_po_line` пересобираются целиком.** Сейчас `distinct` и `row_number()` по всей истории строк — это полная сортировка 5,5 млн строк каждую ночь.
   Что делать: инкремент по `updated_at` с перекрытием (последние 3 дня) и `merge` по ключу `(order_id, line_no)`. Витрину OTIF пересчитывать только для строк, по которым пришли новые приёмки или изменения (список затронутых ключей из stg). Факты партиционировать по месяцу (`planned_delivery_date` / `order_date`), на даты — BRIN-индексы.
3. **As-of join к SCD2 и протяжка курсов через `lateral … order by … limit 1`** на каждую строку.
   Что делать: курсы уже материализованы по дням (`fx_rate_daily`), джойн идёт по равенству. Для поставщика в факте хранится `supplier_sk` (поиск версии один раз при загрузке, а не в каждом отчёте). Индекс `(master_supplier_id, valid_from, valid_to)`.
4. **Проверки качества `not exists` по сырым таблицам.** Перенести их в тесты dbt на инкрементальную часть: проверять новое, а не всю историю.
5. **Если вырастет ещё на порядок** и запросы AI4BI начнут сканировать годы истории: агрегаты «поставщик × месяц» и «позиция × поставщик × месяц» в отдельные таблицы, а LLM-слою отдавать их. Колоночное хранилище (ClickHouse) имеет смысл обсуждать только на этом этапе, не раньше.
